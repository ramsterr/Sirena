```python
# 2. Spectrum-Based Scorer — THE core of MicroRank
class SpectrumScorer:
    def ochiai_score(self, service: str, 
                     anomalous_traces: List[Trace],
                     normal_traces: List[Trace]) -> float:
        """
        Ochiai coefficient:
        score = n_ef / sqrt(n_f * n_e)
        
        Where:
        - n_ef = number of anomalous traces containing this service
        - n_f  = total number of anomalous traces
        - n_e  = total number of traces (anomalous + normal) containing this service
        
        High score = this service appears in many anomalous traces
                    AND few normal traces → likely root cause
        """
        n_ef = sum(1 for t in anomalous_traces if service_in_trace(service, t))
        n_f = len(anomalous_traces)
        n_e = sum(1 for t in (anomalous_traces + normal_traces) 
                  if service_in_trace(service, t))
        
        if n_ef == 0 or n_e == 0:
            return 0.0
        return n_ef / math.sqrt(n_f * n_e)
```

**Key thing to get right:** The time window matters enormously. You're comparing "traces from the last 30 minutes of anomaly" against "traces from the 30 minutes before the anomaly." If you compare against traces from 3 days ago, a deployment might have changed the baseline. Always use a sliding window relative to the incident.

**Test it:** Inject a fault (e.g., add artificial latency to the `cartService`). Run your anomaly detector. It should classify traces that hit `cartService` as anomalous. Run your spectrum scorer. `cartService` should have the highest Ochiai score.

#### Week 4: PageRank + Integration

**Build:**

```python
# 1. Personalized PageRank — MicroRank's final ranking step
class RootCauseRanker:
    def rank(self, dependency_graph: nx.DiGraph, 
             spectrum_scores: Dict[str, float]) -> List[Tuple[str, float]]:
        """
        1. Create a weighted adjacency matrix from the dependency graph
        2. Set personalization vector = normalized spectrum scores
           (services with high spectrum scores get higher "starting importance")
        3. Run PageRank with this personalization
        4. Return ranked list of (service, score) tuples
        """
        # Personalization vector: PageRank will favor nodes that already
        # look suspicious (high spectrum score), but also considers
        # graph structure — a suspicious node with many dependents
        # is more likely the root cause than an isolated suspicious node
        
        personalization = {}
        total = sum(spectrum_scores.values())
        for node in dependency_graph.nodes():
            personalization[node] = spectrum_scores.get(node, 0) / total
        
        ranked = nx.pagerank(dependency_graph, 
                            personalization=personalization,
                            alpha=0.85)  # standard damping factor
        
        return sorted(ranked.items(), key=lambda x: x[1], reverse=True)

# 2. Pipeline Orchestrator — ties everything together
class MicroRankPipeline:
    def run(self, incident_time: datetime, 
            window_minutes: int = 30) -> List[Tuple[str, float]]:
        # Step 1: Fetch traces
        traces = self.fetcher.fetch_recent_traces(incident_time, window_minutes)
        
        # Step 2: Build dependency graph
        graph = self.graph_builder.build_from_traces(traces)
        
        # Step 3: Classify traces
        anomalous, normal = self.detector.split_anomalous_normal(traces)
        
        # Step 4: Spectrum scoring
        scores = {}
        for service in graph.nodes():
            scores[service] = self.scorer.ochiai_score(service, anomalous, normal)
        
        # Step 5: PageRank ranking
        ranked = self.ranker.rank(graph, scores)
        
        return ranked
```

**Key thing to get right:** The `personalization` vector is what makes this "Personalized PageRank" instead of regular PageRank. Without it, PageRank just finds the most *central* node, which is often the frontend (because everything calls it). The personalization forces PageRank to consider both centrality AND suspiciousness.

## Phase 2: Multi-Modal Fusion (Weeks 5–7)

**Goal:** Add metrics as a second signal. Move from "this service appears in bad traces" to "this service has anomalous metrics AND appears in bad traces." This is where you implement the core idea from CHASE.

### What to Extract from the CHASE Paper

| Paper Section | What You Need From It | How You'll Use It |
|---|---|---|
| Multimodal Invocation Graph (Section III-B) | How to attach metric nodes to service nodes in the graph | Each service node gets connected to its metric nodes (CPU, memory, latency, error rate) |

```python
class MetricAnomalyDetector:
    """
    Detect anomalies in Prometheus metrics per service.
    v1: Simple statistical thresholds.
    v2: Replace with 3-sigma or isolation forest.
    """
    
    METRICS_PER_SERVICE = [
        'container_cpu_usage_seconds_total',
        'container_memory_working_set_bytes', 
        'http_server_request_duration_seconds',  # latency
        'http_server_requests_total{status="5xx"}',  # errors
    ]
    
    def detect(self, service: str, 
               incident_time: datetime) -> Dict[str, float]:
        """
        For each metric of this service:
        1. Query Prometheus for baseline (1 hour before incident)
        2. Query Prometheus for current window (incident ± 15 min)
        3. Compare: is current value > 3σ from baseline?
        
        Returns: {metric_name: anomaly_score}
        anomaly_score = (current - mean_baseline) / std_baseline
        """
        scores = {}
        for metric in self.METRICS_PER_SERVICE:
            baseline = self.query_prometheus(metric, service, 
                                             before=incident_time)
            current = self.query_prometheus(metric, service,
                                            around=incident_time)
            
            mean_b = np.mean(baseline)
            std_b = np.std(baseline)
            
            if std_b > 0:
                scores[metric] = abs(np.mean(current) - mean_b) / std_b
            else:
                scores[metric] = 0.0
        
        return scores
    
    def query_prometheus(self, metric, service, **kwargs):
        """Wrapper around PromQL queries"""
        # e.g., rate(http_server_requests_total{service="cart", status="5xx"}[5m])
        pass
```

#### Week 6: Heterogeneous Graph Construction + Fusion

**Build:**

```python
class HeterogeneousGraph:
    """
    Extends the Phase 1 dependency graph with metric nodes.
    
    Graph structure:
    - Service nodes: same as Phase 1
    - Metric nodes: one per (service, metric_name) pair
    - Edges:
      - service→service: call dependencies (from traces)
      - service→metric: "service S exposes metric M" (ownership)
      - metric→service: "metric M influences assessment of S" (reverse)
    """
    
    def build(self, traces: List[Trace], 
              metric_scores: Dict[str, Dict[str, float]]) -> nx.DiGraph:
        G = nx.DiGraph()
        
        # Step 1: Add service nodes and call edges (from Phase 1)
        dep_graph = self.build_dependency_graph(traces)
        G.add_nodes_from(dep_graph.nodes(), type='service')
        G.add_edges_from(dep_graph.edges(), type='calls')
        
        # Step 2: Add metric nodes
        for service, metrics in metric_scores.items():
            for metric_name, score in metrics.items():
                metric_node = f"{service}::{metric_name}"
                G.add_node(metric_node, type='metric', anomaly_score=score)
                G.add_edge(service, metric_node, type='owns')
                G.add_edge(metric_node, service, type='influences')
        
        return G

class FusedScorer:
    """
    Combines trace-based and metric-based anomaly signals.
    
    This is the simplified CHASE fusion.
    v1: Weighted linear combination.
    v2: Attention-based (learn the weights).
    """
    
    def score(self, service: str, 
              trace_score: float,
              metric_scores: Dict[str, float],
              graph_centrality: float,
              alpha=0.4, beta=0.4, gamma=0.2) -> float:
        """
        Fused score = α·trace_signal + β·metric_signal + γ·graph_signal
        
        - trace_signal: from spectrum scoring (Phase 1)
        - metric_signal: max anomaly across all metrics for this service
        - graph_signal: how many other anomalous services depend on this one
          (upstream services with many affected dependents = more likely root cause)
        """
        metric_signal = max(metric_scores.values()) if metric_scores else 0.0
        
        return (alpha * trace_score + 
                beta * metric_signal + 
                gamma * graph_centrality)
```

**Key thing to get right:** The fusion weights (α, β, γ) will make or break your tool. Start with equal weights. Then create a calibration script: inject 10 different fault types, see which weights give the best top-1 accuracy, and fix those weights. Don't over-engineer this — in practice, trace and metric signals are roughly equally important, with graph position as a tiebreaker.

**Key thing to get right:** Granger causality is a *weak* form of causality — it only captures temporal precedence, not true causation. But it's surprisingly effective in microservices because failures really do propagate forward in time. A service can't be affected before the service it depends on fails. Use Granger causality as a *filter*: if A doesn't Granger-cause B, you can eliminate the hypothesis that A's failure caused B's failure.

#### Week 9: Causal Graph Construction

```python
class CausalGraphBuilder:
    """
    Builds a causal graph from:
    1. Service dependency graph (from traces) — structural prior
    2. Temporal ordering (from Phase 3, Week 8) — time-based evidence  
    3. Granger causality scores — statistical evidence
    
    Key insight from OCEAN: the dependency graph is a PRIOR,
    not the final answer. Some dependencies are inactive during
    normal operation. The causal graph only includes edges that
    are ACTIVE during the incident.
    """
    
    def build(self, dependency_graph: nx.DiGraph,
              temporal_order: List[Tuple[str, datetime]],
              granger_scores: Dict[Tuple[str, str], float]) -> nx.DiGraph:
        
        causal_graph = nx.DiGraph()
        causal_graph.add_nodes_from(dependency_graph.nodes())
        
        # Only keep dependency edges that are causally active
        for u, v in dependency_graph.edges():
            # Edge u→v is causal if:
            # 1. u became anomalous BEFORE v (temporal)
            # 2. u Granger-causes v (statistical)
            
            u_onset = dict(temporal_order).get(u)
            v_onset = dict(temporal_order).get(v)
            
            temporal_causal = (u_onset and v_onset and u_onset < v_onset)
            granger_causal = granger_scores.get((u, v), 0) > 0.1
            
            if temporal_causal and granger_causal:
                # Strong evidence: both signals agree
                causal_graph.add_edge(u, v, confidence='high')
            elif temporal_causal or granger_causal:
                # Weaker evidence: only one signal
                causal_graph.add_edge(u, v, confidence='low')
            # else: skip this edge — no evidence it's causal
        
        return causal_graph
```

**Key thing to get right:** Your causal graph will be *sparser* than your dependency graph. That's the point. The dependency graph shows all possible call paths. The causal graph shows which paths *actually transmitted the failure*. A sparse, accurate causal graph is much more useful than a dense dependency graph.

| Multi-Factor Grader (Section 4.2) | How to score a root cause hypothesis from multiple angles | Your confidence scoring — combining trace, metric, temporal, and causal evidence |

### Week 10: Reasoning Path Generation

```python
class ReasoningPathGenerator:
    """
    Generates the "why" behind each root cause ranking.
    Instead of just "inventory-service (94% confidence)", produces:
    
    1. inventory-service → CPU normal, but connection pool: 300/10 (anomalous)
    2. inventory-service → database: connections exhausted 2 min after pool spike
    3. database → payment-service: timeouts started 3 min after DB saturation
    4. payment-service → cart-service: checkout failures 4 min after payment timeouts
    5. cart-service → frontend: user-facing errors 5 min after cart failures
    
    This is the "propagation path" from your mockup.
    """
    
    def generate_path(self, root_cause: str,
                      causal_graph: nx.DiGraph,
                      temporal_order: List[Tuple[str, datetime]],
                      metric_evidence: Dict[str, Dict[str, float]],
                      trace_evidence: Dict[str, float]) -> List[dict]:
        
        path = []
        # BFS from root cause through causal graph
        visited = {root_cause}
        queue = [root_cause]
        
        while queue:
            current = queue.pop(0)
            neighbors = list(causal_graph.successors(current))
            
            for neighbor in neighbors:
                if neighbor not in visited:
                    step = {
                        "from": current,
                        "to": neighbor,
                        "causal_confidence": causal_graph[current][neighbor].get("confidence", "low"),
                        "time_delay": self._time_between(current, neighbor, temporal_order),
                        "evidence": self._collect_evidence(
                            neighbor, metric_evidence, trace_evidence
                        )
                    }
                    path.append(step)
                    visited.add(neighbor)
                    queue.append(neighbor)
        
        return path
    
    def _collect_evidence(self, service, metric_evidence, trace_evidence):
        """
        For each service in the path, collect concrete evidence:
        - Which metrics are anomalous and by how much?
        - How many traces show this service as slow/errored?
        - When did the anomaly start?
        """
        evidence = []
        
        for metric, score in metric_evidence.get(service, {}).items():
            if score > 3.0:  # > 3 sigma
                evidence.append({
                    "type": "metric",
                    "metric": metric,
                    "severity": f"{score:.1f}σ from baseline",
                    "detail": self._get_metric_detail(service, metric)
                })
        
        trace_score = trace_evidence.get(service, 0)
        if trace_score > 0.3:
            evidence.append({
                "type": "trace",
                "severity": f"appears in {trace_score:.0%} of anomalous traces",
            })
        
        return evidence


class MultiFactorConfidence:
    """
    ThinkFL's Multi-Factor Grader, simplified.
    
    Confidence is NOT just the anomaly score.
    It's a combination of:
    1. Anomaly strength (how far from normal?)
    2. Causal evidence (how many downstream services are affected?)
    3. Temporal consistency (did this service fail first?)
    4. Evidence consistency (do traces AND metrics agree?)
    """
    
    def compute(self, service: str,
                anomaly_score: float,
                downstream_affected: int,
                is_earliest: bool,
                signals_agree: bool) -> float:
        """
        Returns 0-100 confidence score.
        """
        score = 0
        
        # Factor 1: Anomaly strength (0-30 points)
        score += min(anomaly_score * 10, 30)
        
        # Factor 2: Downstream impact (0-25 points)
        # Root causes affect many downstream services
        score += min(downstream_affected * 5, 25)
        
        # Factor 3: Temporal priority (0-25 points)
        if is_earliest:
            score += 25
        elif is_earliest is False:  # explicitly not earliest
            score += 5  # small credit for being close to earliest
        
        # Factor 4: Multi-signal agreement (0-20 points)
        if signals_agree:
            score += 20
        
        return min(score, 100)
```

**Key thing to get right:** Every claim must link to evidence. If your tool says "inventory-service connection pool is exhausted," clicking on that should show the Prometheus chart with connections=300 vs baseline=10. SREs will not trust a tool that makes claims without evidence. This is the single biggest adoption barrier.

## Critical Pitfalls to Watch For

### 1. The "Frontend Is Always #1" Problem
PageRank naturally favors highly-connected nodes. In microservices, the frontend/gateway is connected to everything, so it always ranks high. **Fix:** The personalization vector in Phase 1 is essential. Without it, your tool will always say "the frontend is the root cause."

### 2. The "Everything Looks Broken" Problem
When the database fails, every service that uses the database looks anomalous. Your spectrum scorer will flag all of them. **Fix:** The temporal ordering from Phase 3 is the key differentiator — the database's metrics will spike *before* the services that depend on it.

### 3. The "Stale Baseline" Problem
If you compare against metrics from before a deployment, the baseline is wrong. **Fix:** Always use a sliding window baseline (e.g., the 30 minutes immediately before the incident). Never use fixed historical baselines.

### 4. The "Circular Dependency" Problem
Service A calls B, B calls A (common with retries). PageRank handles this fine, but Granger causality doesn't — it assumes no cycles. **Fix:** For Phase 3, use the dependency graph as a structural prior to break cycles. Only compute Granger causality along edges that exist in the dependency graph.

### 5. The "Threshold Sensitivity" Problem
Your anomaly detection thresholds (what z-score counts as "anomalous"?) will need constant tuning. **Fix:** Make them configurable per-service and per-metric. Start with z=3 (99.7% confidence under normality), then adjust based on your test results.

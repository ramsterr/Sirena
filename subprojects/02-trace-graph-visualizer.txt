## Real Objective

You are building a tool that fetches traces from Jaeger and renders the service dependency graph as a visual diagram. Think of it like a map-maker — you're taking raw trace data (who called whom, when, how often) and turning it into a picture that shows the actual call relationships between services. This is the first thing any developer wants to see when they inherit a microservice system: "what talks to what?"

## Tool Objective

By the end of this project, the tool must:
1. Connect to a running Jaeger instance and fetch traces
2. Parse traces to extract service-to-service call relationships
3. Build a directed, weighted graph showing call frequency
4. Render the graph visually (interactive web or static image)
5. Allow filtering by service, time window, and operation
6. Export the graph as JSON or DOT format for further analysis

## What You Must Understand Before Coding

### Concept 1: Jaeger API Trace Structure

The Jaeger API returns traces as JSON with a specific structure. Each trace contains:
- `traceID`: unique identifier for the entire request
- `spans`: array of span objects, each with:
  - `spanID`: unique identifier for this span
  - `parentSpanID`: the span that called this one (empty string if root)
  - `operationName`: what method was called
  - `startTime`: microseconds since epoch
  - `duration`: microseconds
  - `processID`: references the `processes` map
- `processes`: map of processID → `{serviceName, tags}`

**Why this matters:** To build the dependency graph, you need to match each span to its parent span, then extract the service names from the `processes` map. The edge is `parent.serviceName → child.serviceName`.

**Self-check:** Given a span with `processID: "p1"` and `parentSpanID: "abc123"`, how do you find the parent's service name? Answer: Look up the span with `spanID: "abc123"` in the same trace, get its `processID`, then look up that processID in the `processes` map.

### Concept 2: Directed Graphs and Edge Weights

A directed graph (DiGraph) has nodes and directed edges. In your case:
- Nodes = service names
- Edges = "A calls B" (directed from caller to callee)
- Edge weight = how many times this call was observed

NetworkX is the Python library for this. `nx.DiGraph()` creates a directed graph. `G.add_edge("A", "B", weight=5)` adds an edge from A to B with weight 5.

**Why this matters:** The graph structure is what you'll visualize. Edge weights determine line thickness or labels. Node degree (number of connections) can determine node size.

**Self-check:** If service A calls B 50 times, B calls C 30 times, and A calls C 20 times, what does the graph look like? Answer: Three nodes (A, B, C). Three edges: A→B (weight=50), B→C (weight=30), A→C (weight=20). A has out-degree 2, C has in-degree 2.

## What to Code

### Component 2.1: Jaeger Trace Fetcher

**Purpose:** Fetch traces from Jaeger API and return structured data.

**Input:** Service name (optional), time window
**Output:** List of parsed trace objects

**What to understand when coding this:**

The Jaeger API endpoint: `GET http://<jaeger-url>/api/traces?service=<service>&lookback=<duration>`

- `lookback` format: `1h`, `30m`, `15m`
- If no service is specified, fetch all traces (but this can be very large)
- Response is paginated — check `total` in the response and fetch more if needed

Parse the response into Python dataclasses:
```python
@dataclass
class Span:
    trace_id: str
    span_id: str
    parent_id: Optional[str]
    service_name: str
    operation_name: str
    start_time: datetime
    duration_ms: float

@dataclass
class Trace:
    trace_id: str
    spans: List[Span]
```

**How to verify it works:**
- Fetch traces for `frontend` service with `lookback=1h`
- Print the first trace's span count and service names
- Verify the same trace exists in the Jaeger UI by traceID

### Component 2.2: Dependency Graph Builder

**Purpose:** Build a directed, weighted graph from traces.

**Input:** List of Trace objects
**Output:** NetworkX DiGraph with weighted edges

**What to understand when coding this:**

For each trace:
1. Build a map of `span_id → span` for quick parent lookup
2. For each non-root span (where `parent_id` is not None/empty):
   - Find the parent span
   - Edge = `parent.service_name → child.service_name`
   - Increment the edge weight

After processing all traces:
- Nodes are unique service names
- Edges have a `weight` attribute (call count)
- Optionally add `avg_duration_ms` and `p95_duration_ms` as edge attributes

**How to verify it works:**
- Build the graph from 1000 traces
- Print nodes: should be ~11 services for Online Boutique
- Print edges: should match the known architecture (frontend calls multiple services, database is called by multiple services)
- Edge weights should reflect actual call frequency (frontend→cartService should be high, frontend→emailService should be lower)

### Component 2.3: Graph Renderer

**Purpose:** Visualize the dependency graph.

**Input:** NetworkX DiGraph
**Output:** Interactive HTML or static image

**What to understand when coding this:**

Two rendering options:

**Option A: pyvis (interactive HTML)**
```python
from pyvis.network import Network

net = Network(height="750px", width="100%", directed=True)
for node in G.nodes():
    net.add_node(node, label=node, size=G.degree(node) * 5)
for u, v, data in G.edges(data=True):
    net.add_edge(u, v, title=f"calls: {data['weight']}")
net.show("dependency_graph.html")
```

**Option B: graphviz (static image)**
```python
import graphviz
dot = graphviz.Digraph()
for node in G.nodes():
    dot.node(node)
for u, v, data in G.edges(data=True):
    dot.edge(u, v, label=str(data['weight']))
dot.render("dependency_graph", format="png")
```

**How to verify it works:**
- Render the graph. The frontend should be on the left (or top) with edges flowing to downstream services.
- The database should have many incoming edges.
- Edge labels or thickness should reflect call frequency.

### Component 2.3b: Per-Edge Lag Window Computer (Optional)

**Purpose:** Derive per-edge lag windows from trace data for use in causal analysis.

**Input:** NetworkX DiGraph with span duration data on edges
**Output:** Dictionary mapping `(source, target) → max_lag_minutes`

**What to understand when coding this:**

This component computes the P99 span duration for each edge and converts it to a lag window:

```python
def compute_edge_lag_windows(graph: nx.DiGraph) -> dict[tuple[str, str], float]:
    edge_lag_windows = {}
    for u, v, data in graph.edges(data=True):
        durations = data.get('durations', [])
        if durations:
            p99 = np.percentile(durations, 99)
            lag_minutes = max(1.0, min(30.0, (p99 / 1000 / 60) * 10))
        else:
            lag_minutes = 10.0  # fallback
        edge_lag_windows[(u, v)] = lag_minutes
    return edge_lag_windows
```

**How to verify it works:**
- Sync edges (frontend→cart-service) should have ~1 minute windows.
- Async edges (cart-service→email-service) should have 15-30 minute windows.
- Export as JSON for use by the Incident Timeline Generator.

### Component 2.4: CLI Interface

**Purpose:** Command-line interface for fetching and rendering graphs.

**Commands:**
```bash
# Fetch and render the full graph
trace-graph render --jaeger-url http://localhost:16686 --lookback 1h

# Filter by a specific service (show only its neighbors)
trace-graph render --service cartservice --lookback 30m

# Export as JSON
trace-graph export --jaeger-url http://localhost:16686 --output graph.json

# Export as DOT format
trace-graph export --format dot --output graph.dot

# Export per-edge lag windows for causal analysis
trace-graph lag-windows --jaeger-url http://localhost:16686 --output lag_windows.json
```

## Understanding Checkpoints

1. "Can I fetch traces from Jaeger and parse them into my Span/Trace dataclasses?" — If no, the Jaeger API response format is different than expected.
2. "Does the rendered graph match the known Online Boutique architecture?" — If no, your parent-child span matching logic is wrong.
3. "Can I filter the graph to show only the neighbors of a specific service?" — If no, add graph traversal (BFS/DFS from the target node).
4. "Do per-edge lag windows correctly distinguish sync vs async edges?" — If no, check your P99 calculation and the `* 10` safety multiplier.

## Common Mistakes

1. **Not handling missing parent spans.** Some traces have spans whose parent is in a different trace (rare but possible). Skip these edges or log a warning.
2. **Using service name from the span's process without checking the processes map.** The `processID` must be resolved through the `processes` map to get the actual service name.
3. **Overwhelming the Jaeger API.** Fetching all traces for a long time window can return thousands of traces. Use reasonable time windows and pagination.
4. **Not storing span durations on edges.** The per-edge lag window computer needs the raw duration list per edge, not just the call count. Store `durations: List[float]` as an edge attribute.

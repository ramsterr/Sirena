## Real Objective

You are building a tool that proves your RCA pipeline actually works — with numbers, not anecdotes. This is the transition from "it works on my machine" to "I can prove it works." It injects controlled faults, runs the full pipeline, measures accuracy, and produces comparison reports showing how each phase improves on the previous one.

For employers reviewing your portfolio: the benchmark report is the single most convincing artifact. It shows you didn't just build something — you measured it, and it works.

For yourself: you cannot improve what you can't measure. The benchmark suite is how you calibrate thresholds, tune fusion weights, and know exactly where the tool is strong (latency injection) and weak (gradual memory leaks).

## Tool Objective

By the end of this project, the benchmark suite must:
1. Define 5+ fault scenarios with expected root causes
2. Use Project 3 (Fault Injection Toolkit) to inject and clean up faults automatically
3. Run ALL pipeline phases against each scenario: Phase 1 (trace-only, Project 2), Phase 2 (fused, Project 4), Phase 3 (causal, Project 5)
4. Compute standard evaluation metrics: Top-1 Accuracy, Top-3 Accuracy, Mean Reciprocal Rank (MRR), Average Rank
5. Produce a side-by-side comparison report showing improvement across phases
6. Measure per-scenario detection time (how long from fault injection to correct detection)
7. Support custom fault scenarios defined via YAML/JSON

## What You Must Understand Before Coding

### Concept 1: Evaluation Metrics for Root Cause Analysis

**Top-k Accuracy:** Is the actual root cause in the top-k ranked services?
- **Top-1:** Is it ranked #1? (Most important — SREs look at the first result first)
- **Top-3:** Is it in the top 3? (Practical — SREs will check the top 3)
- **Top-5:** Is it in the top 5? (Forgiving — useful for complex multi-cause incidents)

**Average Rank:** Mean rank of the actual root cause across all scenarios. Lower is better. 1.0 = perfect.

**Mean Reciprocal Rank (MRR):** MRR = (1/|Q|) × Σ(1/rank_i). MRR = 1.0 = perfect (#1 every time). MRR = 0.5 = typically ranked #2.

**Why Top-1 matters most:** At 3 AM, the SRE wants ONE answer. If your tool says "it might be A, B, or C," the SRE has to investigate all three — marginally better than no tool. Top-1 accuracy is the metric that determines whether your tool saves time or adds noise.

**Self-check:** Tool ranks root cause as #1 in 3/5 scenarios, #2 in 1, #4 in 1. What are Top-1, Top-3, and MRR? Answer: Top-1 = 3/5 = 60%. Top-3 = 4/5 = 80%. MRR = (1/1+1/1+1/1+1/2+1/4)/5 = (1+1+1+0.5+0.25)/5 = 0.75.

### Concept 2: Fault Scenario Structure

Each scenario defines: what fault to inject, where, what propagation to expect, and what the correct answer is.

```yaml
scenarios:
  - name: "CPU saturation on payment-service"
    inject:
      type: cpu_stress
      target_service: paymentservice
      params:
        cores: 4
        duration: 300
    wait_seconds: 300          # allow propagation
    expected_root_cause: "payment-service"
    expected_top3_candidates: ["payment-service", "database"]  # loose match
    signals:                   # which signals should fire
      trace: "weak"            # CPU stress has weak trace signal
      metric: "strong"         # CPU metric should spike hard
    note: "Tests whether Phase 2 metric fusion catches what Phase 1 trace-only misses."

  - name: "Network latency on cart-service"
    inject:
      type: latency
      target_service: cartservice
      params:
        amount: 500
    wait_seconds: 300
    expected_root_cause: "cart-service"
    signals:
      trace: "strong"
      metric: "moderate"
    note: "Tests baseline trace-only detection (Phase 1 should catch this easily)."

  - name: "Database connection contention"
    inject:
      type: cpu_stress
      target_service: database
      params:
        cores: 4
        duration: 300
    wait_seconds: 300
    expected_root_cause: "database"
    signals:
      trace: "moderate"
      metric: "strong"
    note: "Tests 'everything looks broken' scenario. Many services show anomalies but DB is upstream root cause. Tests causal graph (Phase 3)."

  - name: "Partial pod crash (scale down)"
    inject:
      type: scale_down
      target_deployment: cartservice
    wait_seconds: 300
    expected_root_cause: "cart-service"
    signals:
      trace: "strong"
      metric: "strong"
    note: "Tests capacity fault. Both trace and metric signals should fire."

  - name: "Error injection (bad deploy)"
    inject:
      type: error_injection
      target_deployment: recommendationservice
    wait_seconds: 300
    expected_root_cause: "recommendation-service"
    signals:
      trace: "strong"
      metric: "strong"
    note: "Tests software fault. Error rate should spike in both traces and metrics."
```

## What to Code

### Component 7.1: Scenario Runner

**Purpose:** Execute a single fault scenario end-to-end: inject → wait → analyze → evaluate → cleanup.

**Input:** Scenario definition (YAML/JSON)
**Output:** ScenarioResult with rankings from all pipeline versions and accuracy metrics

```python
@dataclass
class ScenarioResult:
    scenario_name: str
    expected_root_cause: str
    phase1_ranked: list[tuple[str, float]]   # Project 2 output
    phase2_ranked: list[tuple[str, float]]   # Project 4 output
    phase3_ranked: list[tuple[str, float]]   # Project 5 output
    phase1_rank: int                          # rank of expected root cause
    phase2_rank: int
    phase3_rank: int
    phase1_top3: bool
    phase2_top3: bool
    phase3_top3: bool
    detection_time_seconds: float             # from injection to first correct detection
    injection_success: bool
    cleanup_success: bool
    errors: list[str]                         # any errors during the run

def run_scenario(scenario: dict,
                 injector_bin: str = "fault-inject",
                 microrank_bin: str = "microrank",
                 rca_detect_bin: str = "rca-detect",
                 causal_trace_bin: str = "causal-trace") -> ScenarioResult:
    # 1. Inject fault
    inject_result = subprocess.run(
        [injector_bin, "inject", "--type", scenario["inject"]["type"],
         "--service", scenario["inject"]["target_service"],
         *flatten_params(scenario["inject"].get("params", {})),
         "--output", "json"],
        capture_output=True, text=True
    )
    if inject_result.returncode != 0:
        return ScenarioResult(..., errors=[f"Injection failed: {inject_result.stderr}"])

    injection_data = json.loads(inject_result.stdout)
    incident_time = injection_data["injected_at"]

    # 2. Wait for propagation
    wait = scenario.get("wait_seconds", 300)
    time.sleep(wait)

    # 3. Run Phase 1 (trace-only, Project 2)
    phase1_output = subprocess.run(
        [microrank_bin, "analyze", "--graph", "graph.json",
         "--executions", "executions.json", "--output", "json"],
        capture_output=True, text=True
    )
    phase1_data = json.loads(phase1_output.stdout) if phase1_output.returncode == 0 else None

    # 4. Run Phase 2 (fused, Project 4)
    phase2_output = subprocess.run(
        [rca_detect_bin, "analyze", "--incident-time", incident_time,
         "--baseline-window", "60", "--incident-window", "15",
         "--graph", "graph.json", "--output", "json"],
        capture_output=True, text=True
    )
    phase2_data = json.loads(phase2_output.stdout) if phase2_output.returncode == 0 else None

    # 5. Run Phase 3 (causal, Project 5)
    phase3_output = subprocess.run(
        [causal_trace_bin, "analyze", "--metrics", "metrics.json",
         "--graph", "graph.json", "--lag-windows", "lag_windows.json",
         "--format", "json", "--output", "-"],
        capture_output=True, text=True
    )
    phase3_data = json.loads(phase3_output.stdout) if phase3_output.returncode == 0 else None

    # 6. Clean up fault
    subprocess.run([injector_bin, "cleanup", "--all"])

    # 7. Evaluate
    expected = scenario["expected_root_cause"]
    return ScenarioResult(
        scenario_name=scenario["name"],
        expected_root_cause=expected,
        phase1_ranked=extract_ranked(phase1_data),
        phase2_ranked=extract_ranked(phase2_data),
        phase3_ranked=extract_ranked(phase3_data),
        phase1_rank=find_rank(phase1_data, expected),
        phase2_rank=find_rank(phase2_data, expected),
        phase3_rank=find_rank(phase3_data, expected),
        # ... compute top-3, detection time, etc.
    )
```

**Key requirements:**
- Idempotent: clean up ALL faults before starting a new scenario (regardless of prior run state)
- Timeout: if any pipeline step hangs, timeout after 5 minutes and record as error
- Recovery wait: after cleanup, wait 5-10 minutes before next scenario (let the system stabilize)
- Concurrent pipelines: Phase 1, 2, 3 can run concurrently (they don't depend on each other's output) — use `concurrent.futures.ThreadPoolExecutor`

### Component 7.2: Metrics Calculator

**Purpose:** Compute aggregate evaluation metrics from scenario results.

**Input:** List of ScenarioResult
**Output:** EvaluationReport with Top-1, Top-3, MRR, Average Rank per phase

```python
@dataclass
class EvaluationReport:
    total_scenarios: int
    per_phase: dict[str, PhaseMetrics]  # "phase1" → metrics, "phase2" → metrics, ...
    per_scenario: list[ScenarioResult]
    comparison_table: str               # formatted table

@dataclass
class PhaseMetrics:
    top1_accuracy: float     # 0.0 to 1.0
    top3_accuracy: float
    top5_accuracy: float
    mean_reciprocal_rank: float
    average_rank: float
    failures: int            # number of scenarios where pipeline errored

def compute_metrics(results: list[ScenarioResult]) -> EvaluationReport:
    phases = ["phase1", "phase2", "phase3"]
    per_phase = {}
    for phase in phases:
        ranks = [getattr(r, f"{phase}_rank") for r in results if getattr(r, f"{phase}_rank") is not None]
        n = len(ranks)
        if n == 0:
            per_phase[phase] = PhaseMetrics(0, 0, 0, 0, 0, len(results))
            continue
        top1 = sum(1 for r in ranks if r == 1) / n
        top3 = sum(1 for r in ranks if r <= 3) / n
        top5 = sum(1 for r in ranks if r <= 5) / n
        mrr = sum(1/r for r in ranks) / n
        avg_rank = sum(ranks) / n
        per_phase[phase] = PhaseMetrics(top1, top3, top5, mrr, avg_rank,
                                         len(results) - n)
    # ... build comparison table
    return EvaluationReport(len(results), per_phase, results, build_table(results, per_phase))
```

### Component 7.4: CLI Interface

```bash
# Run all scenarios
rca-benchmark run --scenarios scenarios.yaml

# Run a specific scenario
rca-benchmark run --scenario "CPU saturation on payment-service"

# Compare two pipeline versions explicitly
rca-benchmark compare --baseline phase1 --candidate phase3

# Custom pipeline binary paths
rca-benchmark run --scenarios scenarios.yaml \
    --injector-bin ./fault-inject \
    --microrank-bin ./microrank \
    --rca-detect-bin ./rca-detect \
    --causal-trace-bin ./causal-trace

# Output report to file
rca-benchmark run --scenarios scenarios.yaml --output benchmark-report.md

# JSON output for CI/CD
rca-benchmark run --scenarios scenarios.yaml --output results.json --format json

# Dry-run (print what would happen without injecting)
rca-benchmark run --scenarios scenarios.yaml --dry-run
```

## Understanding Checkpoints

1. "Can I explain why Top-1 accuracy matters more than Top-3 for incident response?" — The SRE wants ONE answer. A list of 3 candidates still requires manual investigation. Top-1 measures whether the tool actually saves time.
2. "Can I explain the difference between MRR and Average Rank?" — MRR weights higher ranks more heavily (1/rank). Average Rank is linear. If one scenario has rank=10, MRR penalizes it heavily (adds 0.1), while Average Rank adds 10. MRR is the standard IR metric.
3. "Does the comparison report clearly show Phase 3 outperforming Phase 1?" — If not, either Phase 3 has a bug, or your test scenarios don't exercise causal graph advantages (try DB contention scenario).
4. "Can a new user add a custom fault scenario without modifying code?" — If no, make `scenarios.yaml` fully declarative.

## Common Mistakes

1. **Not waiting long enough after injection.** 300 seconds is minimum for propagation. CPU stress might need 5+ minutes before downstream services show effects.
2. **Not cleaning up between scenarios.** A leftover fault from scenario 1 contaminates scenario 2. Always run `fault-inject cleanup --all` before AND after each scenario.
3. **Not waiting for recovery between scenarios.** After cleanup, the system needs 5-10 minutes to stabilize (latency returns to baseline). Running the next scenario too soon uses corrupted baseline data.
4. **Comparing against wrong expected root cause.** The expected root cause should be the faulted SERVICE, not a downstream victim. If you inject CPU stress on `cart-service`, the expected root cause is `cart-service`.
5. **Using hardcoded binary paths.** Allow CLI overrides (`--microrank-bin`) so the benchmark works in different environments.
6. **Not handling pipeline errors gracefully.** If Project 4 crashes (Prometheus down), record the error and continue with remaining scenarios. Don't abort the entire run.

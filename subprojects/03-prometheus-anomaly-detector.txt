## Real Objective

You are building a standalone tool that queries Prometheus for service metrics and flags when they deviate from normal behavior. Think of it like a health monitor — it knows what "normal" looks like for each service's CPU, memory, latency, and error rate, and it raises an alert when something crosses the threshold. This is a reusable component that any team can plug into their monitoring pipeline, independent of traces or root cause analysis.

## Tool Objective

By the end of this project, the tool must:
1. Query Prometheus for key metrics per service (CPU, memory, latency, error rate)
2. Compute baseline statistics from a historical window
3. Detect anomalies using z-scores (and optionally MAD)
4. Output a report of anomalous services and metrics
5. Support configurable thresholds and time windows
6. Provide a programmatic API (Python library) and a CLI

## What You Must Understand Before Coding

### Concept 1: Z-Score Anomaly Detection

The z-score measures how many standard deviations a value is from the mean:

`z = (current_value - baseline_mean) / baseline_std`

Interpretation:
- `|z| > 2`: mild anomaly (5% chance under normal distribution)
- `|z| > 3`: strong anomaly (0.3% chance)
- `|z| > 5`: critical anomaly (essentially impossible under normal distribution)

**Why this matters:** This is the core detection algorithm. It's simple, fast, and effective for most production metrics. The key is computing the baseline correctly — it must be from a period when the system was known to be healthy.

**Self-check:** A service's baseline CPU mean is 45%, std is 8%. Current CPU is 78%. What's the z-score? Is it anomalous? Answer: z = (78 - 45) / 8 = 4.125. Yes, strongly anomalous (> 3).

### Concept 2: PromQL Query Patterns for Key Metrics

You need four PromQL queries per service:

**CPU usage (counter → rate):**
```promql
100 * rate(container_cpu_usage_seconds_total{container!="POD", namespace="default"}[5m])
```

**Memory usage (gauge → direct):**
```promql
container_memory_working_set_bytes{container!="POD", namespace="default"}
```

**P95 latency (histogram → percentile):**
```promql
histogram_quantile(0.95,
  sum(rate(http_server_request_duration_seconds_bucket{namespace="default"}[5m]))
    by (le, service)
)
```

**Error rate (counter → ratio of rates):**
```promql
100 * sum(rate(http_server_requests_total{status=~"5..", namespace="default"}[5m])) by (service)
  / sum(rate(http_server_requests_total{namespace="default"}[5m])) by (service)
```

**Why this matters:** Each metric type requires a different PromQL approach. Using the wrong query (e.g., reading a counter directly instead of using `rate()`) produces garbage data.

**Self-check:** Why does CPU use `rate()` but memory doesn't? Answer: CPU is a counter (cumulative, only goes up), so you need `rate()` to get the per-second usage. Memory is a gauge (current value), so you read it directly.

### Concept 3: PELT Changepoint Detection (Advanced Onset Detection)

Z-score detection flags anomalies when individual points cross a threshold. **PELT changepoint detection** (Pruned Exact Linear Time) finds the moment the entire distribution of a time series shifts — the mean, variance, or both change.

Why PELT matters for this project:
- **Gradual anomalies:** A memory leak might not cross 3σ for minutes after it started. PELT detects the onset at the beginning of the shift.
- **Regime shifts:** During an incident, the time series distribution changes. Z-scores assume stability; PELT does not.
- **Onset accuracy:** PELT gives onset times accurate to ±1 minute, which is critical for causal timeline construction.

```python
import ruptures as rpt

def detect_changepoint(metric_series: np.ndarray, 
                       baseline_window: int = 60) -> Optional[int]:
    algo = rpt.Pelt(model="l2", min_size=3).fit(metric_series)
    change_points = algo.predict(pen=10)
    
    for cp in change_points:
        if cp > baseline_window:
            return cp
    return None
```

**When to use which:**
- Use **z-scores** for real-time anomaly flagging (fast, simple, good for dashboards).
- Use **PELT** for onset detection when building incident timelines (more accurate, handles gradual anomalies).

**Self-check:** A memory leak starts at 02:12 and grows linearly for 20 minutes. Z-score detection might not trigger until 02:18. PELT detects the shift at ~02:13. Which method gives a more accurate onset time? Answer: PELT.

## What to Code

### Component 3.1: Prometheus Query Client

**Purpose:** Query Prometheus for metric time series data.

**Input:** PromQL query, time range
**Output:** Time series as list of (timestamp, value) tuples

**What to understand when coding this:**

The Prometheus API endpoint: `GET http://<prometheus-url>/api/v1/query_range?query=<promql>&start=<start>&end=<end>&step=<step>`

- `start` and `end`: Unix timestamps in seconds
- `step`: data point interval (e.g., `60s` for one point per minute)
- Response format:
```json
{
  "data": {
    "result": [
      {
        "metric": {"service": "cart-service", ...},
        "values": [[1609459200, "45.2"], [1609459260, "47.1"], ...]
      }
    ]
  }
}
```

Parse the response: each entry in `values` is `[unix_timestamp, string_value]`. Convert timestamp to datetime and value to float.

**How to verify it works:**
- Query `up` (a built-in metric that shows target health). Should return 1 for healthy targets.
- Query a service-specific metric. Should return time series data with timestamps and values.

### Component 3.2: Baseline Calculator

**Purpose:** Compute baseline statistics from a historical time window.

**Input:** Time series data from baseline window
**Output:** Mean, standard deviation, and optionally MAD for the time series

**What to understand when coding this:**

For each (service, metric) pair:
1. Fetch the time series from the baseline window (e.g., 60 minutes before the incident)
2. Compute mean and standard deviation
3. If std is 0 (metric never changed), use MAD instead:
   - MAD = median(|x_i - median(x)|)
   - robust_std = 1.4826 * MAD
4. Store baseline as: `{service: {metric: {mean, std, mad}}}`

**How to verify it works:**
- Compute baseline for a service running normally. Mean and std should be reasonable (CPU ~30-60%, std ~5-15%).
- Compute baseline for a service with no data. Should return None or raise a clear error.

### Component 3.3: Anomaly Detector

**Purpose:** Compare current metrics against baseline and flag anomalies.

**Input:** Baseline statistics, current time series
**Output:** Dictionary mapping `metric_name → z_score` for each service, plus optional onset time

**What to understand when coding this:**

For each (service, metric):
1. Fetch the current time series (incident window)
2. For each data point, compute z-score: `(value - baseline_mean) / baseline_std`
3. The anomaly score for this metric = maximum absolute z-score in the current window
4. Flag as anomalous if `max_z_score > threshold` (default 3.0)

**Optional: PELT onset detection.** When the `--detect-onset` flag is used, also run PELT changepoint detection on the combined baseline + incident time series to find the exact onset time:

```python
import ruptures as rpt

def detect_onset(metric_series: np.ndarray, 
                 timestamps: np.ndarray,
                 baseline_window: int = 60) -> Optional[datetime]:
    algo = rpt.Pelt(model="l2", min_size=3).fit(metric_series)
    change_points = algo.predict(pen=10)
    
    for cp in change_points:
        if cp > baseline_window:
            return timestamps[cp]
    return None
```

Output format (with onset detection):
```python
{
    "cart-service": {
        "cpu": {
            "z_score": 4.2, 
            "anomalous": True, 
            "current_value": 78.5, 
            "baseline_mean": 45.0,
            "onset_time": "2026-05-19T02:13:00Z"  # from PELT
        },
        "memory": {"z_score": 1.1, "anomalous": False, "current_value": 512.0, "baseline_mean": 498.0},
        "latency_p95": {"z_score": 5.8, "anomalous": True, "current_value": 1200.0, "baseline_mean": 200.0},
        "error_rate": {"z_score": 0.3, "anomalous": False, "current_value": 0.02, "baseline_mean": 0.01}
    }
}
```

**How to verify it works:**
- Run on normal data. All z-scores should be < 2.
- Inject CPU stress. The CPU z-score for the affected service should exceed 3.
- Inject network latency. The latency z-score should exceed 3, but CPU should remain normal.
- With `--detect-onset`, the onset time should be within ±2 minutes of the actual fault injection time.

### Component 3.4: CLI and Library API

**Purpose:** Provide both a CLI and a Python library interface.

**CLI commands:**
```bash
# Detect anomalies
prom-anomaly detect --prometheus-url http://localhost:9090 --baseline-window 60m --incident-window 15m

# Detect anomalies for a specific service
prom-anomaly detect --service cartservice

# Detect anomalies with PELT onset detection
prom-anomaly detect --detect-onset

# Output as JSON
prom-anomaly detect --output json --output-file anomalies.json

# Set custom threshold
prom-anomaly detect --threshold 2.5
```

**Library API:**
```python
from prom_anomaly import PrometheusAnomalyDetector

detector = PrometheusAnomalyDetector(prometheus_url="http://localhost:9090")

# Basic z-score detection
anomalies = detector.detect(
    baseline_window_minutes=60,
    incident_window_minutes=15,
    threshold=3.0
)

# With PELT onset detection
anomalies = detector.detect(
    baseline_window_minutes=60,
    incident_window_minutes=15,
    threshold=3.0,
    detect_onset=True  # runs PELT changepoint detection
)
```

## Understanding Checkpoints

1. "Can I write a PromQL query for P95 latency from memory?" — If no, study PromQL more.
2. "Can I explain why z-scores are better than fixed thresholds?" — If no, re-read Concept 1.
3. "Can I explain why PELT changepoint detection is better than z-score thresholding for onset detection?" — If no, re-read Concept 3. (PELT detects distribution shifts, not individual point crossings. It handles gradual failures like memory leaks much better.)
4. "Does the detector correctly flag anomalies when I inject a fault?" — If no, check your baseline window and PromQL queries.

## Common Mistakes

1. **Using the incident window's own statistics instead of the baseline.** If the anomaly is already happening, the current mean will be skewed. Always use the baseline period's statistics.
2. **Querying counters directly without `rate()`.** Raw counter values are meaningless — they're cumulative since process start.
3. **Not handling missing data.** If a service has no data in the baseline window, the detector should report "insufficient baseline data" rather than crashing or producing NaN z-scores.
4. **Using z-score threshold crossing for onset detection.** For timeline accuracy, use PELT changepoint detection instead. Z-scores are fine for flagging anomalies, but PELT gives more accurate onset times.

## Real Objective

You are building a tool that takes incident data and automatically generates a structured postmortem document. Think of it like an automated incident reporter — it takes the raw data (what broke, when, what the metrics looked like, what the root cause was) and produces a well-formatted markdown document that a team can use for their incident review. This saves hours of manual documentation and ensures consistency across postmortems.

## Tool Objective

By the end of this project, the tool must:
1. Accept incident data (root cause, timeline, metrics, affected services)
2. Generate a structured markdown postmortem with standard sections
3. Support customizable templates
4. Include metric charts (as embedded images or links)
5. Output as markdown file or display in terminal
6. Include actionable sections: impact, root cause, timeline, remediation steps, lessons learned

## What You Must Understand Before Coding

### Concept 1: Postmortem Structure

A standard postmortem includes:
1. **Summary:** One-line description of the incident
2. **Impact:** Who/what was affected and for how long
3. **Timeline:** Chronological list of events
4. **Root Cause:** What caused the incident
5. **Resolution:** How it was fixed
6. **Lessons Learned:** What went well, what went wrong
7. **Action Items:** Follow-up tasks to prevent recurrence

**Why this matters:** The postmortem generator must produce a document that follows this structure. Each section maps to specific input data.

**Self-check:** Given a root cause of "database connection pool exhaustion," what would the summary look like? Answer: "On [date], the inventory-service experienced connection pool exhaustion, causing cascading failures in payment-service, cart-service, and frontend, resulting in 5xx errors for ~15% of user requests for 20 minutes."

## What to Code

### Component 8.1: Postmortem Template Engine

**Purpose:** Render a postmortem from incident data using a template.

**Input:** Incident data dictionary
**Output:** Formatted markdown string

**What to understand when coding this:**

Default template structure:
```markdown
# Incident Postmortem

## Summary
{{ summary }}

## Impact
- **Affected services:** {{ affected_services | join(", ") }}
- **Duration:** {{ duration }}
- **User impact:** {{ user_impact }}

## Timeline
| Time | Event |
|------|-------|
{% for entry in timeline %}
| {{ entry.time }} | {{ entry.event }} |
{% endfor %}

## Root Cause
{{ root_cause }}

### Evidence
{% for service, evidence in evidence.items() %}
- **{{ service }}:** {{ evidence }}
{% endfor %}

## Resolution
{{ resolution }}

## Lessons Learned
### What went well
{% for item in what_went_well %}
- {{ item }}
{% endfor %}

### What went wrong
{% for item in what_went_wrong %}
- {{ item }}
{% endfor %}

## Action Items
| Task | Owner | Due Date |
|------|-------|----------|
{% for item in action_items %}
| {{ item.task }} | {{ item.owner }} | {{ item.due_date }} |
{% endfor %}
```

### Component 8.2: Data Collector

**Purpose:** Gather incident data from the root cause analysis pipeline.

**Input:** Root cause result, timeline, metric anomalies
**Output:** Incident data dictionary ready for template rendering

**What to understand when coding this:**

The data collector maps the output of the RCA pipeline to the postmortem template fields:
- `root_cause` → from the ranked root cause result
- `timeline` → from the incident timeline generator
- `affected_services` → from the causal graph (all downstream services)
- `evidence` → from the metric anomaly detector and spectrum scorer
- `summary` → auto-generated from root cause + affected services + duration

### Component 8.3: CLI Interface

**Purpose:** Command-line interface for postmortem generation.

**CLI commands:**
```bash
# Generate from incident data file
postmortem generate --input incident.json

# Generate from RCA pipeline output
postmortem generate --rca-output results.json --timeline timeline.json

# Output to file
postmortem generate --input incident.json --output postmortem.md

# Use custom template
postmortem generate --input incident.json --template custom_template.md

# Display in terminal
postmortem generate --input incident.json --display
```

## Understanding Checkpoints

1. "Can I map the RCA pipeline output to the postmortem template fields?" — If no, review the data structures from the RCA pipeline.
2. "Does the generated postmortem include all standard sections?" — If no, check your template.
3. "Does the auto-generated summary accurately describe the incident?" — If no, refine your summary generation logic.

## Common Mistakes

1. **Generating a postmortem with placeholder text.** The tool should fill in as much as possible from the data. Only leave placeholders for sections that require human input (like "lessons learned" and "action items").
2. **Not handling missing data.** If some fields are not available (e.g., no timeline data), the postmortem should still generate with those sections marked as "pending."
3. **Overly technical language.** The postmortem should be readable by non-technical stakeholders. Avoid jargon in the summary and impact sections.
